Speaker Lab Handbook

A plain-language guide for anyone joining the work: what the lab is, who does what, and how a job runs. Claude keeps it up to date; the history of changes is in CHANGELOG.md.

00Quick start

Type labs in a terminal. The startup routine runs by itself: it tidies up, flags anything critical, lists projects by date, offers one random idea, and asks what to work on.

labsStart and catch up
labStart
labcContinue the last session

The shortcuts need these three lines in ~/.zshrc (once per computer). Without them: cd ~/speaker-lab then claude.

lab()  { cd ~/speaker-lab && claude "$@"; }
labs() { cd ~/speaker-lab && claude "/startup"; }
labc() { cd ~/speaker-lab && claude -c; }

Several sessions at once (macOS)

Cmd + ` cycles between terminal windows, Cmd + Shift + ] or [ between tabs, Cmd + N opens a new window, Cmd + T a new tab. For a second session, open another terminal and type lab.

Where to put files

Papers and scans in corpus/raw/, other source files in corpus/data/, exports from old chats in inbox/. Or email them to Claude's inbox: /startup downloads attachments into inbox/email/ and asks where they go. Processed exports move to inbox/done/, which is kept out of git.

You can't forget a step: a check runs at the start of every session and Claude acts on it.

01What it is

A folder you open in Claude Code. Claude acts as chief engineer and hands specialist work to a team of AI "subagents", each with one job. Everything learned is written to files, so research is done once and every new build starts from what earlier builds found out.

02How you use it

Talk to it in plain language. You don't need to know any commands: Claude runs them and the subagents for you. Say what you're thinking about, even if it's vague, and it will:

  1. Ask questions, mostly multiple choice, each with its own recommendation and a "you decide" option.
  2. Explain the trade-offs where a choice needs background.
  3. Pick the next step, say what it's running, and run it.
  4. End every reply with the next question or the next action.

Say "you decide" to skip a question, or "fewer questions" to turn the questioning down. The commands further down are shortcuts for when you know what you want.

Model choice (since 14 Nov 2026)

Each agent runs on the cheapest model that does its job reliably. Fable is kept for checking and for the maths a print or purchase rests on. Claude moves a single job up a tier when it is unusually hard (a research question that is mostly derivation, a new sim method, a tricky CAD split) and down a tier when it is routine, and says so in the one-line plan.

The main session cannot change its own model. Switch it yourself with /model:

CommandWhen
/model opusEveryday work, ideas, research, planning (the default)
/model fableA /build or design review session, or when a result looks wrong and needs the strongest reasoning
/model sonnetQuick record-keeping (ideas, notes, inventory)
/model opusplanThe only automatic switch: Opus in plan mode, Sonnet once it starts doing the work. Not advised for /build or reviews, where the orchestrating needs Opus or Fable

Claude will suggest a switch in one line when the work calls for it, in both directions: up when the job needs it, down when a strong model is being spent on something trivial (an email, simple sums, notes). Haiku suits one-line lookups and trivial edits. The project default is set in .claude/settings.json ("model": "opus").

06How a build runs

  1. Idea. Logged in projects/IDEAS.md; notes added as they come.
  2. Start. /new-project writes the spec, pulls in lessons from earlier builds and lists owned kit that could be used.
  3. Research. Library first, then the web. Anything out of reach goes on the request list for Tek.
  4. Checks first. The verification engineer writes the tests before any simulation or print file exists.
  5. Design. Maths, then simulation, then the 3D model. Each hands over to the next through files.
  6. Release. The print file must pass every automated check and an independent slicer, and gets a version number.
  7. Review. Four fresh reviewers look at the numbers, the file, the data and the report.
  8. Build and measure. A small test print first, then the part, then measurements against stated pass criteria.
  9. Learn. Results, decisions and lessons are written back so the next build benefits.

07The automatic check

tools/check.py runs at the start of every session. It reports papers not yet ingested, exports not imported, files in the wrong folder, missing setup files, verification that's out of date, and open requests and to-dos. Claude fixes what it can and tells you what only you can do. Run it by hand with python3 tools/check.py.

09Running more than one session

Open several terminals in the folder and run claude in each, for example one ingesting papers while another takes ideas. They share the same files and usage allowance. Avoid two sessions doing the same job on the same project.

When Claude runs agents in parallel that write to the same record, it removes duplicates before committing. After an import it compares the export's answers with the project spec and shows you any conflicts with both dates, rather than asking again.

Agents re-read any file immediately before writing it and append to existing files rather than overwrite, so one session's agent can't wipe another session's work.

10The rules everyone follows

  • Library before web, and never research the same thing twice.
  • Every claim is cited, with the source's weight (1 to 5). Decisions need solid sources or our own verified result.
  • Maths is done in code, not estimated.
  • Checks are written by someone other than the designer, before the thing they check, and each is proven by planting a fault it must catch.
  • The exported file is checked against the design, not against the program that made it.
  • Predictions are estimates. Nothing is final until measured; crossovers are set only from measurements of the finished speaker.
  • Reports list what is verified and what is not.
  • Decisions are logged with the reason and the evidence.
  • Briefs name only checked sources. An author or paper named in an agent brief must be in corpus/index.md or knowledge/source-weighting.md; any other name is marked "(unverified)" so the agent checks it before raising a request.
  • Missing sources are requested, not ignored. Any agent that wants a paper or book we lack logs it; urgent ones are listed at the start of every session.
  • No unnecessary language from any agent or in any file, without cutting information.

13Changing the setup

Each agent is a short text file in .claude/agents/, and each command one in .claude/commands/. Edit the text to change the behaviour. Ask Claude to make the change and it will update this handbook and the changelog.
